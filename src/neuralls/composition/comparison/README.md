# Comparison workflow

Composition for comparing preconditioners on one system. The entry point runs every configured preconditioner on the same input and collects the results. Aggregating results *across* several sibling systems (a comparison group's projected scaling-law metric) is orchestrated from `composition/assignments/comparison_batch.py`; this package holds the pieces — `groups.py` (data-driven group discovery and its up-front validations) and `group_reporting.py` (classifying and reporting each group through the `GroupReportSink` port) — while `compare_preconditioners` itself only ever sees one system at a time.

## Modules

- `comparison_run.py`: one comparison run across all configured preconditioners. Pure orchestration; I/O and algorithms are delegated. `compare_preconditioners` takes an optional `cache: GroupPreconditionerCache | None` — when the caller is running one sibling of a `comparison_sweeps` group, this lets a preconditioner built for an earlier sibling be reused instead of rebuilt (see `_preconditioner_setup.py`).
- `config_assembler.py`: builds `ComparisonConfig` from the case registry, defaults and per-method overrides. `resolve_comparison_config` also resolves `notation_policy` (a `NotationPolicy`, `Cosmetic()`-marked on `ComparisonConfig` so it never affects reuse identity): the case's `[comparison_baseline.presentation]` by default, fully replaced (not field-merged) by a per-entry `method` file's own `[presentation]` table when present — same full-replace precedence `preconditioners`/`normalize_system` already use here.
- `_input_resolution.py`, `source_handlers.py`: resolve the input system from a canonical right-hand-side source, one handler per source kind.
- `_linear_system.py`: loads and normalizes the linear system.
- `rhs_generation.py`: direct right-hand-side generators.
- `_preconditioner_setup.py`: creates preconditioners, their schedules, input bindings and the stopping criterion. Also owns `GroupPreconditionerCache`, scoped to one comparison group (`by_matrix`): it reuses a built preconditioner across sibling systems only when doing so is provably valid — always for a `torchalg.StaticSetupPreconditioner` (setup never reads the matrix), or for a `torchalg.MatrixSetupPreconditioner` only when every sibling resolves to the same matrix. A cache hit copies forward the real one-time `setup_cost`/peak-memory measurement rather than reporting a misleadingly-free 0.0.
- `_generation_cost.py`: the dataset-generation cost attributed to a comparison (`resolve_generation_cost`), and whether that cost is a one-time artifact or reruns per system (`resolve_generation_repeatability` — a `GenerationRepeatability`, driven by checkpoint presence on the resolved config, not by preconditioner type).
- `result_keys.py`: stable result-key names — each config's own `.name`, a `@computed_field` derived from its type and distinguishing fields (`platform/config/models/preconditioner.py::preconditioner_slug`), never user-typed. Two configs with identical fields produce the identical key and are rejected as duplicates by `validate_unique_preconditioner_keys`; this is intentional (they're the same preconditioner), not a bug. Changing a key's *derivation* breaks stored results the same way changing it used to.
- `_presentation.py`, `_plots.py`: labels and diagnostic plots for one run.
- `models.py`: the composition-layer DTOs of the workflow.

- `pinned_split.py::resolve_matrix_index`: the one place that decides which raw matrix index a comparison entry addresses (a `test_position` selects a test-fold matrix unless the RHS source is the dataset itself); shared by group discovery and the runner so a cache's "same matrix" proof and the matrix actually loaded cannot drift.
