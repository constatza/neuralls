# Comparison workflow

Composition for comparing preconditioners. `plan.py` defines concrete matrix/RHS systems, `recipes.py` defines their report identities, and `spec_consistency.py` validates method identity across datasets. Aggregate reporting accepts canonical matrix-setup and RHS-solve events only; `group_reporting.py` deliberately does not rebuild those events from denormalized `CGComparisonResult` rows.

## Modules

- `comparison_run.py`: `execute_method_workload` runs one resolved method over ordered matrix/RHS bundles and returns a frozen `CompletedMethodWorkload`. Each matrix has one timed setup whose prepared object serves its sibling RHS solves; checkpoint objects live for the method, while prepared matrix state is released before the next matrix. It requires the method's `PreparedMethodPresentation` (which must belong to the method) plus the `DatasetPresentation` of every dataset it runs on and the case's `NotationPolicy`, which name the method and dataset in its warning lines, and carries, with the canonical events, the family/color/marker style map and an `ExecutedMethod`: right after each matrix's one setup, `_preconditioner_setup.capture_system_realizations` reads the realized facts from the built preconditioner once and records a `SystemRealization` for every sibling RHS system, then the preconditioner is released, so reporting never rebuilds or keeps it. A failure reading those facts is a labelling failure, not a method outcome: it raises `RealizedFactCaptureError` carrying a `ComparisonMatrixFailureContext` (phase `REALIZED_FACT_CAPTURE`, method, dataset, matrix) and stops the workload. A method whose every setup failed has an `ExecutedMethod` with no systems; the workload refuses a presentation that belongs to a different method. Its optional offline cost is historical generation only; checkpoint/data I/O remains outside the benchmark cost model and all online totals. A setup or solve failure is a recoverable scientific outcome: it emits a contextual warning and remains in the canonical events for aggregation and MLflow failure counts. Orchestration, persistence, and reporting failures are blocking exceptions and are never converted into these events.
- `config_assembler.py`: builds `ComparisonConfig` from the case registry, defaults and per-method overrides. `resolve_comparison_config` also resolves `notation_policy` (a `NotationPolicy`, `Cosmetic()`-marked on `ComparisonConfig` so it never affects reuse identity): the case's `[comparison_baseline.presentation]` by default, fully replaced (not field-merged) by a per-entry `method` file's own `[presentation]` table when present — same full-replace precedence `preconditioners`/`normalize_system` already use here.
- `_input_resolution.py`, `source_handlers.py`: resolve the input system from a canonical right-hand-side source, one handler per source kind. `resolve_comparison_source` is also the one place the source's `mask` (any kind) is applied, on its own random stream, dropping `lhs` of a masked system. The raw handlers' `validate` also rejects an external vector whose length differs from the native matrix's order, failing only that system. `resolve_comparison_input` requires the planner's `matrix_provenance`, which every `ResolvedComparisonInput` carries.
- `_linear_system.py`: loads and normalizes the linear system.
- `rhs_generation.py`: direct right-hand-side generators (`gaussian`, `sinusoidal`).
- `_preconditioner_setup.py`: creates preconditioners, schedules and input bindings, and `capture_system_realizations`, which turns a just-built preconditioner into per-system realized facts without another setup. Parameter arrays and inline POD/neural-POD fit arrays are staged before setup timing; device/dtype conversion, fitting, hierarchy construction and binding occur inside the measured setup. The retained legacy cache is matrix-scoped for both static and matrix-dependent preconditioners, so no prepared object crosses a matrix boundary.
- `_generation_cost.py`: the dataset-generation cost attributed to a comparison (`resolve_generation_cost` reads the manifests; the pure `aggregate_generation_cost` sums their recorded times and takes the largest peak memory), and whether that cost is a one-time artifact or reruns per system (`resolve_generation_repeatability` — a `GenerationRepeatability`, driven by checkpoint presence on the resolved config, not by preconditioner type).
- `result_keys.py`: stable result-key names — each config's own `.name`, a `@computed_field` derived from its type and distinguishing fields (`platform/config/models/preconditioner.py::preconditioner_slug`), never user-typed. Two configs with identical fields produce the identical key and are rejected as duplicates by `validate_unique_preconditioner_keys`; this is intentional (they're the same preconditioner), not a bug. Changing a key's *derivation* breaks stored results the same way changing it used to.
- `_plots.py`: the diagnostic plots for one run. `_generate_comparison_plots` takes a typed `Legend` and `FigureTitle` (rendered when each figure is drawn). Each run records its preconditioners' plot styles (the prepared method presentation plus family and colour/marker keys) on `ComparisonResult.plot_styles`, which group reports reuse. A run that did not converge has `[did not converge]` appended to its legend entry in every per-run plot (`Legend.marking_unconverged`), so a capped run is never read as cheap.
- `ComparisonPresentation` (`models.py`): the prepared cohort, the comparison title and the case's notation; `build_comparison_result_from_diagnostics` takes it from the preflight instead of describing configs again.
- `recipes.py`: `rhs_recipe` (the one definition of an RHS recipe: kind plus the parameters that make problems differ, plus the mask; a raw vector source is identified by its row and a fingerprint of its path, row kind and scale) and `system_tag` (a `PlannedSystem`'s `SystemTag` from `domain.solver.models.benchmark_events` for the metrics table).
- `spec_consistency.py`: `validate_dataset_specs_consistent`.
- `system_figures.py`: after every method workload has finished (never inside a timed region), builds the merged convergence table from the workloads' diagnostics and draws, per system, one residual and one energy-error figure holding every method that has a history for it (the energy figure is skipped when all its values are null). Figure directories and names come from the dataset/recipe presentation, never raw ids; `run_comparison_batch` uploads them under `system_figures/<system>` of the session run together with the session-level `convergence.parquet`.
- `group_reporting.py`: flattens completed workloads into canonical setup/solve events and classifies matrix-set-and-RHS-type, matrix-set and all-matrix-sets groups; it never fabricates timing from diagnostic result rows. Each group's `GroupPresentation.methods` holds, per method, its prepared presentation plus the realized facts that `reduce_realized_facts` finds identical on every system of that group, so a matrix-varying fact such as operator depth is never claimed for the group but stays in the workload's per-system realizations. `report_all_levels` requires the dataset presentations and the case's `NotationPolicy` (it names a skipped group by its scope) and puts a typed `GroupScope` (recipe, dataset or all datasets) on each `GroupPresentation`; a group on a dataset without one raises `MissingDatasetPresentationError`. Distinctness of methods is decided on structured facts at preflight; no key is appended to a label.
- `models.py`: the composition-layer DTOs, including frozen/slotted `ResolvedMethod`, `MatrixWorkload`, `MatrixWorkloadMember`, and `CompletedMethodWorkload` (which carries the stable method config digest and the realized-or-prepared method presentation alongside its canonical events).
- `plan.py`: `plan_comparisons` / `plan_systems` run once after `input_gate.require_current_inputs` and produce the `PlannedSystem`s (`models.py`) that config resolution, the runner and reporting all consume. It is the only place that decides which matrix, which RHS row and which RHS seed a system uses: `[[comparisons]]` needs a single-matrix dataset, `[[comparison_sweeps]]` a multi-matrix one (`FirstNSelector`/`FractionSelector` over the pinned test fold's matrices), `rhs_count` draws per matrix of a `seeded` source get independent seeds from `derive_seed` (a `single_draw` source must have `rhs_count = 1`; both traits live on the source model), and the matrix's provenance (`SharedSingleMatrix`/`HeldOutMatrix`, never absent) is attached to the plan. It also rejects shape-rule violations, duplicate planned ids and datasets of differing system size.
- `input_gate.py`: refuses datasets generation has not produced and pinned under the current config, or that carry no scientific provenance (identity cannot see that, so it raises `StageInputsStale` naming `neuralls generate --force`). Dataset directories come from `config_assembler.resolve_dataset_dir`.
