# Review of the FCG submission timing audit

This review evaluates `/home/archer/Documents/phd/submissions/fcg/notes/ours/code-audit.md` and `timing.md` against this repository at commit `31949e8`, its locked `torchalg` revision `3c8904116fb5128005469677f579de47675ff4b8` (`uv.lock`), primary numerical and benchmarking sources, and the supplied spectral-3d report export. The export provides figure cards and derived tables, but not the source method event files, run environment or generating code revision. No experiment or timing was rerun.

## Verdict

The audit correctly identifies the split between per-matrix setup, per-RHS solve, and historical offline costs, and finds real accounting hazards in lazy spectral-radius estimation and repeated coarse solves. Its blanket statements about the direction and size of performance bias, ranking stability, and what reviewers will accept are not established by source inspection. Most importantly, it incorrectly says **every** AMG variant performs a coarse LU solve: adaptive SA-AMG and bootstrap AMG use a pseudo-inverse in this case. The paper should not inherit that error.

The report supports accounted online and whole-run-cost comparisons **within the tested dense implementations**, conditional on source-run provenance and with success interpreted as the solver's stated stopping outcome. On its stated 20-system workload, the exported POD-2G full totals exceed Jacobi's and aggregation AMG's totals, though they remain below the adaptive and bootstrap AMG outliers. They cannot be generalized to a different reuse workload or tuned sparse solvers, and they do not correct the possible A1 timing omission.

## Scientific checks the audit should add

1. **PCG assumptions are a method-design question, not a per-run certification task.** A fixed linear preconditioner must also have the symmetry and positivity properties appropriate for CG. Document or review the AMG construction when changing its smoother or coarse solve; there is no evidence here that the current runs violate those assumptions and no need to test every realized operator before reporting ordinary solver convergence. [PETSc KSPCG](https://petsc.org/main/manualpages/KSP/KSPCG.html) documents the requirements; [Notay (2000)](https://doi.org/10.1137/S1064827599362314) addresses variable preconditioning.
2. **The true residual is an optional diagnostic, not a second required success rule.** It is freshly computed as \(b-Ax_k\) from known quantities, without knowing the exact solution. The solver normally stops using its cheaper recursively updated residual; this is a standard convergence outcome. The code records the fresh residual after timing without changing that outcome, which is reasonable. Inspect it if there is evidence of a material discrepancy, but do not relabel every solve or block speed claims on a second threshold. [PETSc's KSP manual](https://petsc.org/release/manual/ksp/) likewise distinguishes the convergence norm from a true-residual monitor.
3. **Damping formulas differ by role.** Relaxation uses \(\omega=1/\rho(D^{-1}A)\); aggregation's prolongation smoothing uses \(\omega=(4/3)/\rho(D^{-1}A)\). The appendix wording in `timing.md` section 7 should not state one formula for both. The estimate is iterative and cached by tensor identity, not “per preconditioner instance.”
4. **The proposed A1 ranking argument is not evidence.** A single representative-matrix timing screens for scale but does not bound the omitted cost over five different matrices and several methods. Nor is “reported time is a lower bound” mathematically guaranteed in a noisy median experiment. Show raw paired samples and either rerun or construct a defensible workload-wide bound before a numerical ranking claim.
5. **The literature comparison is limited.** Six papers do not establish a field norm or what a reviewer will ask. The original POD-2G study's inclusion of initial simulations and training supports full-cost accounting for its own workload, not a numerical expectation here ([Nikolopoulos et al., 2024](https://doi.org/10.1002/nme.7372)). GPU synchronization around asynchronous work is appropriate ([PyTorch CUDA semantics](https://docs.pytorch.org/docs/stable/notes/cuda.html)); median repeats are also ordinary benchmark practice ([PyTorch benchmark utilities](https://docs.pytorch.org/docs/stable/benchmark_utils.html)).

## Planning order and evidence needed

1. **Establish provenance before qualifying the existing table.** Use the exported session run ID and method-run IDs to recover source revision, locked dependency revision, device/CPU/thread count, and stored `setup_events`/`solve_attempts` with repeat samples. The export already has method config digests. Confirm these match the code reviewed here. If they do not, re-audit the generating revision.
2. **State the solver outcome precisely.** Report the exported converged counts as tolerance-based solver outcomes; identity converged on 0/20 systems. Keep the stored fresh residual as a diagnostic to inspect if a discrepancy appears. Review PCG symmetry/positivity assumptions when changing AMG construction, not as a routine gate on this run.
3. **Resolve the one-off accounting.** Measure the spectral estimate on each report matrix and affected hierarchy level; inspect the setup and first-RHS repeat distributions. Distinguish a disclosed omitted setup phase from a corrected rerun. Update equations and appendix wording with both damping roles and the actual coarse-solve variant.
4. **Explain baseline outliers.** Profile adaptive SA-AMG and bootstrap AMG at the tested settings, including hierarchy construction, coarse pseudo-inverse, smoothing, and solve iteration counts. Compare like-for-like dense implementations; claim no general advantage over optimized sparse AMG.
5. **Interpret the exported full cost for its actual workload, then define any new deployment scenario.** For the reported 20 systems, the four POD full totals already include known offline stages and exceed Jacobi's and aggregation AMG's totals. For other workloads, state how many new matrices and RHS reuse one trained basis, charge generation and fit/run exactly once per basis, and keep unavailable stages unavailable. Use complete workload totals with failure counts; label online-only projections separately. Five matrix draws alone do not justify a general break-even law.
6. **Clean up lower-impact issues after the science is secure.** Reject unsupported fixed-iteration settings, correct memory/warm-up documentation, and retire the stale sweep script. These do not repair the existing paper numbers.
